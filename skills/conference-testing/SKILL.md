# Проверка конференций

Выбери проверки по изменению и существующим средствам проекта. Сначала изучи
команды CI и тесты. Не добавляй новый тестовый фреймворк ради единичной проверки.

## Уровни проверки

| Изменение | Значимые проверки |
| --- | --- |
| Комнаты и API | создание, вход, лимит участников, закрытие, неверный запрос, отказ в доступе |
| Конкурентность | одновременный вход на последнее место, повторный выход, disconnect старой сессии после reconnect |
| Сигналинг | адресация, изоляция комнат, неизвестный тип, неверный payload, медленный клиент, обрыв |
| WebRTC | два браузера, двусторонние треки, mute/unmute, выход, повторный вход, отказ камеры, relay через TURN |
| SFU | несколько участников до заявленного лимита, подписки, выход издателя, нагрузка на медиа |

Для Go после существенных изменений запускай `go test ./...`, `go vet ./...`
и `go build ./...`; для конкурентного кода — `go test -race ./...` в поддерживаемом
окружении. Применяй `gofmt` к изменённым Go-файлам. При отсутствии модуля сначала
реализуй запрошенный код; не создавай модуль только ради успешной команды.

В интеграционных тестах используй изолированные комнаты, управляемые дедлайны
и очистку ресурсов. Ожидай события с таймаутом вместо произвольных sleep.
Успешный обмен SDP не доказывает передачу медиа: проверь поступление треков
и рост счётчиков полученных байтов/кадров через `getStats()`.

Для браузерной автоматизации используй fake media там, где это поддерживается;
проверку реальных устройств и разрешений выдели отдельно. Если браузер или TURN
недоступен, укажи непроверенный сценарий и воспроизводимые шаги ручной проверки.

Нагрузку на сигналинг измеряй отдельно от нагрузки на медиа. В отчёте сохраняй
условия: число комнат/участников, длительность, bitrate, CPU, память и ошибки.
Не заявляй поддержку размера конференции по результатам одного API-бенчмарка.
