# Архитектура веб-конференций

Изучи текущий код, требования и `docs/architecture.md` в корне проекта, если
он существует. Для mvp1 пользователь уточнил сценарий публикации серверных
Firefox/terminal, максимум два пользователя, роли и администратора, лёгкую БД,
TURN, управление и локальную печать через DataChannel. Не подменяй этот сценарий
обычной конференцией с камерами пользователей. Неутверждённые решения помечай
как предложения.

## Порядок решений

1. Выясни из задачи размер комнаты, целевую нагрузку, способы входа и размещение.
   Если ответ не блокирует работу, запиши допущение и продолжай независимую часть.
2. Раздели управление комнатами, сигналинг и передачу медиа. WebSocket переносит
   управляющие сообщения; аудио и видео передаются по WebRTC.
3. Для звонков один на один рассмотри P2P. Для групповых звонков оцени SFU,
   исходящий трафик клиентов и серверную полосу. Не выдавай mesh-демо за
   масштабируемое решение; фиксируй пределы выбранной топологии.
4. При необходимости SFU сравни интеграцию готового сервера с собственным
   компонентом на Go. Собственный SFU требует отдельного обоснования сложности.
   Библиотека WebRTC сама по себе не является готовым конференц-сервером.
5. Начни с одного Go-сервиса, если задача не требует иного. БД добавляй для
   устойчивых данных; Redis и распределённый сигналинг — по реальной необходимости.
   Для состояния в памяти явно укажи потерю комнат после рестарта и один экземпляр.

## Результат

Зафиксируй принятое решение и критерии проверки в `docs/architecture.md`:
сценарии MVP, допущения, топология, границы компонентов, хранение, ограничения.
Для существенного выбора добавь короткую ADR с альтернативами и последствиями.

Ориентир структуры при реализации: `cmd/server`, `internal/rooms`,
`internal/signaling`, `internal/config`, `web`, `docs`. Добавляй транспорт,
хранилище и медиакомпоненты только при наличии соответствующего кода.
Первый вертикальный сценарий mvp1 — вход пользователя, каталог разрешённых
приложений, запуск серверного Firefox, изображение по WebRTC, управление через
DataChannel и корректный выход. Второй пользователь проверяет лимиты и выбранную
модель изоляции либо совместной работы. Двустороннее аудио/видео с камер не входит
в этот сценарий без отдельного требования.
