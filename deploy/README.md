# Рабочий запуск mvp1

Каталог предназначен для рабочего стенда. Реализован `run.sh` для Go gateway
с HTTPS и отдельной SQLite, `runtime.sh` для runner и `worker/Dockerfile`.
Порядок запуска и параметры сети описаны в [runbook](../docs/runbook.md).
PDF-печать реализована через Go IPP и DataChannel; coturn требует настройки сети.
Для многоузлового Kubernetes используйте [отдельную инструкцию](kubernetes/README.md)
и `build-images.sh`: зависимости приложений включены в образы.

Серверная платформа — Linux. Пользовательский браузер может работать на Linux,
Windows и macOS; отдельное клиентское приложение в MVP не требуется.
Возможный будущий Electron-клиент описан в
[ADR-004](../docs/adr/004-client-platforms-and-mvp-experience.md).

## Состав

- Go gateway, HTTPS/WSS и локальная SQLite.
- Локальный Go runner и поддерживаемый контейнерный runtime.
- До четырёх контейнеров сеансов (два пользователя × два приложения):
  Falkon, Firefox либо terminal, Go worker, Xvfb,
  оконный менеджер, FFmpeg; виртуальная PDF-печать.
- coturn в согласованном сетевом сегменте, доступном обеим сторонам.

Пример конфигурации coturn: `turnserver.conf.example`. Зависимости Go закреплены
в go.mod/go.sum. Изоляция процессов worker описана в ADR-006.

## Данные и конфигурация

SQLite, секреты, сертификаты, профили и spool размещаются в отдельных volumes
рабочего запуска. Реальные файлы с паролями не попадают в репозиторий.
Логины и пароли задаёт оператор; начального общего пароля администратора нет.
Рабочие volumes никогда не используются тестовым compose-проектом.

Для запуска потребуются адрес HTTPS, доверенный клиентом TLS-сертификат,
адрес TURN, listener/relay-порты, TURN shared secret, разрешённые сетевые
назначения приложений и лимиты ресурсов. Отдельный IP для TURN/TLS на 443
понадобится, если этого требует клиентская сеть и 443 уже занят HTTPS.

До развёртывания уточняются Linux-дистрибутив, CPU/RAM/GPU, расположение NAT,
доступные UDP/TCP направления. Профили одноразовые, terminal — изолированная shell.
Эти сведения влияют на параметры запуска, но не требуют изменения каталога,
SQLite и общей модели прав.

## Проверка запуска

Проверить готовность gateway и runner, запуск одного приложения, внешний
WebRTC-сеанс через принудительный TURN relay, ввод и доставку PDF. Затем
повторить с двумя пользователями и двумя приложениями у каждого (четыре сеанса).
Будущее расширение до трёх приложений на пользователя потребует проверки
ресурсов для шести сеансов. Переход к отдельному API gateway описан в
[ADR-003](../docs/adr/003-api-gateway-evolution.md).
Проверка HTTP health endpoint сама по себе
не подтверждает доступность медиа, приложений и печати.

При остановке gateway запрещает новые сеансы, runner завершает приложения
с дедлайном, workers закрывают WebRTC, временные профили и spool очищаются.
Одноразовые профили подтверждены в ADR-005. Очистка контейнеров проверена
локальным интеграционным тестом; внешний рабочий стенд ещё не проверен.

## Запуск текущего gateway

В корне проекта задайте `MVP_ADMIN_LOGIN` и `MVP_ADMIN_PASSWORD` для создания
первой учётной записи, затем `MVP_PUBLIC_ORIGIN`, `MVP_TLS_CERT`, `MVP_TLS_KEY`.
Запустите `./deploy/run.sh`. По умолчанию слушается `0.0.0.0:8443`; origin
должен совпадать с фактическим адресом в браузере, включая порт.
БД расположена в `deploy/data/mvp1.db`, не в `testing/data/`.
На повторных запусках bootstrap-пароль не меняет существующую учётную запись.
Полный пример ввода пароля без записи в историю: [README](../README.md).
