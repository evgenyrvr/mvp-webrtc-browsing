# Тестирование mvp1

Каталог предназначен для отдельного интеграционного и браузерного стенда.
Добавлены `run.sh` для локального gateway и `check.sh` для Go-проверок.
Медиастенд запускается через `build-worker.sh` и `runtime.sh`; порядок описан
в [runbook](../docs/runbook.md). `rtc-check.sh` проверяет Pion/DataChannel,
`docker-check.sh` — приложения в контейнерах. Матрица ниже содержит также
будущие проверки, которые ещё не выполнены.

Запуск: задайте bootstrap-логин и пароль по [README](../README.md), затем
`./testing/run.sh`. Адрес — `http://127.0.0.1:8080`, отдельная БД —
`testing/data/mvp1.db`. Проверки: `./testing/check.sh`; для race detector нужен GCC
или Clang. Unit-тесты используют временные SQLite и fake-runtime только в тестах.

Проверка реального HTTP-процесса: `python3 testing/smoke.py`. Нужен доступ
к localhost sockets. Выполнены Go-тесты, vet, сборка, race detector и HTTP smoke.
Браузерная автоматизация на Linux выполнена; матрица Windows/macOS остаётся
для проверки на соответствующих клиентах. Результаты — в [verification.md](verification.md).

## Изоляция запуска

Runner использует namespace `mvp1-testing`, интеграционный Docker-тест —
`mvp1-integration`. Сети, SQLite, профили и порты отделены от `deploy/`.
Контейнеры теста удаляются при завершении. Unit-тесты остаются рядом с пакетами.

## Матрица приёмки

Приоритет — полный [клиентский путь MVP](../docs/adr/004-client-platforms-and-mvp-experience.md)
на Linux, Windows и macOS с Linux-сервером. Для каждой ОС фиксируются версии
браузера, прохождение сценария и непроверенные возможности. Проверить вход,
каталог, запуск, реальную работу в двух приложениях, печать, reconnect и выход.
Оценивать читаемость текста, удобство ввода и понятность состояний интерфейса.
Electron пока не входит в тестовый стенд MVP.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Пользователь с доступом только к Firefox | Видит Firefox; запуск terminal напрямую через API запрещён |
| Администратор назначает роль | Каталог и серверные проверки отражают назначение |
| Отзыв launch/control/print | Сеанс закрыт либо действие блокируется, включая уже открытый DataChannel |
| Два пользователя, по два приложения | Четыре независимых сеанса: профили, изображение, ввод и задания печати |
| Firefox и terminal в разных вкладках | Оба активны; смена вкладки не завершает приложение и сбрасывает зажатые клавиши |
| Третье приложение одного пользователя | Запуск отклонён даже при наличии свободного общего слота |
| Третий активный пользователь или пятый сеанс | Нет лишнего контейнера; возвращена понятная ошибка лимита |
| Два конкурирующих запуска на последнее место | Резерв получает только один; ошибка запуска освобождает слот |
| Закрытие или reconnect одного приложения | Второе приложение того же пользователя продолжает работать |
| Logout или отключение пользователя | Все приложения этого пользователя завершены; другой пользователь не затронут |
| Chrome → Firefox | Видно изменяющееся содержимое; растут media counters в getStats |
| RU/EN и сочетания | Текст, Shift/Ctrl/Alt, повтор, раскладки работают по согласованной матрице |
| Изменение размера клиентского окна | Координаты клика соответствуют изображению |
| Потеря фокуса при зажатой клавише | Клавиша отпущена на сервере |
| Печать со страницы Firefox | Через DataChannel доставлен корректный PDF, локальная печать доступна |
| Большой PDF во время ввода | Очередь ограничена, управление остаётся работоспособным |
| Разрыв при доставке PDF | Нет испорченного документа и повторной автоматической печати |
| Чужой session/job ID | Отказ без раскрытия изображения и документа |
| TURN relay-only | По статистике выбран relay, работают видео, ввод и PDF |
| UDP заблокирован на клиенте | Проверены TURN/TCP и TURN/TLS при разрешённой серверной сети |
| Reconnect в grace period | Восстановлено своё приложение; старое соединение не принимает ввод |
| Выход, отзыв прав, рестарт сервера | Процессы, display, spool и слот корректно освобождены |
| Доступ к внутренним адресам | Разрешённые назначения доступны, запрещённые блокируются сетью |
| Terminal | Shell/фиксированная команда соответствует утверждённому шаблону |

Для медиапроверок нужны реальные браузерные endpoints. Моки SDP не заменяют
проверку доставки видео. Физическую печать проверять вручную на целевой ОС клиента;
автотест подтверждает доставку PDF, но не выход бумаги из принтера.

В отчёте фиксировать версии Chrome/Firefox, серверное оборудование, разрешение,
fps, bitrate, задержку ввода, RAM/CPU и выбранный ICE transport. Численные SLA
устанавливаются после согласования сети и измерений. Тесты не должны создавать
реальные задания печати без явного тестового сценария пользователя.

### TURN relay

`./testing/turn-check.sh 192.168.15.38 udp` (или `tcp`) поднимает временный
coturn на порту 3479 с relay-портами 52150–52199 и запускает браузерный тест
с принудительным relay. Подставьте LAN IP этой машины. Docker и Firefox
должны быть установлены. Контейнер и временный секрет удаляются после проверки.
Тест проверяет выбранную relay-пару, непрерывное видео и ввод в терминал.
Локальный запуск не заменяет испытание через внешний NAT или TURN TLS.

Браузерный тест также отправляет PDF на IPP внутри контейнера и проверяет
полученный Blob в клиентском браузере по SHA-256. Он не печатает на физическое
устройство. `MVP_PRINT_DIALOG_TEST=1` дополнительно сохраняет снимок диалога
серверного Firefox в `/tmp/mvp1-print-dialog.png` для проверки обнаружения принтера.

### Четыре одновременных приложения

`./testing/docker-check.sh` запускает два Firefox и два terminal в отдельных
контейнерах с четырьмя Pion-клиентами. Проверяются рост RTP каждую секунду
в течение 10 секунд, ввод через DataChannel, изоляция файлов терминалов,
отзыв управления при продолжающихся старых heartbeat и работа остальных
трёх потоков после закрытия первого приложения. Тест выводит снимок CPU/RAM/PIDs.

Это проверка runtime на четырёх сеансах, а не четырёх браузерных вкладок
двух авторизованных пользователей. Пользовательские лимиты проверяются
отдельно в Go-тестах API/менеджера сеансов. Контейнеры удаляются после теста.

### Два пользователя в четырёх браузерных вкладках

```bash
MVP_BROWSER_MULTI=1 MVP_BROWSER_LAN_IP=192.168.15.38 ./testing/browser-check.sh
```

Подставьте LAN IP сервера. Этот режим использует два независимых профиля
Firefox и временную БД. Администратор через API создаёт обычных пользователей
и назначает доступ к приложениям; затем каждый пользователь открывает два
сеанса в отдельных вкладках. Проверяется рост декодированных кадров без
переподключений, HTTP 409 для третьего приложения, HTTP 403 для административного
API и HTTP 404 для чужого сеанса. Logout первого пользователя должен удалить
только его контейнеры; оба приложения второго продолжают передавать видео.
Создание пользователей и запуск сеансов выполняются через API из браузера;
ручное заполнение форм и клики по каталогу этот сценарий не покрывает.

### Chromium на серверной машине

```bash
MVP_BROWSER_LAN_IP=192.168.15.38 ./testing/browser-check.sh
```

При создании и удалении Docker-интерфейсов локальный Chromium может прервать
HTTP-запрос с `ERR_NETWORK_CHANGED`. Поэтому Chromium-режим подготавливает и
удаляет сеансы отдельным Go HTTP-клиентом с обычной авторизацией/CSRF.
Вход в клиентский браузер, WebRTC, декодирование, ввод, получение PDF и перехват
сеанса проверяются в Chromium. Этот режим не подтверждает работу кнопок
запуска/завершения из Chrome на этой же серверной машине; их нужно проверить
с отдельного клиентского компьютера. Firefox-режим выполняет эти API-запросы
непосредственно из браузера.

## Falkon и Kubernetes backend

После сборки worker image:

```sh
MVP_BROWSER_KIND=firefox MVP_BROWSER_APP=falkon MVP_PRINT_DIALOG_TEST=1 \
  MVP_WORKER_IMAGE=mvp1-worker:pilot MVP_BROWSER_LAN_IP=YOUR_LAN_IP ./testing/browser-check.sh
MVP_BROWSER_KIND=firefox MVP_BROWSER_APP=falkon MVP_BROWSER_MULTI=1 \
  MVP_WORKER_IMAGE=mvp1-worker:pilot MVP_BROWSER_LAN_IP=YOUR_LAN_IP ./testing/browser-check.sh
python3 -m unittest testing/kubernetes_manifest_test.py
```

Прогоны браузера выполнять последовательно: у них общий namespace контейнеров.
`MVP_BROWSER_APP` выбирает серверное приложение, `MVP_BROWSER_KIND` — тестовый
клиент. IP заменить текущим адресом машины. Проверка диалога печати использует
стартовую страницу и геометрию 1280×720; полученный PDF проверяется в клиенте.
Тесты Kubernetes API входят в `testing/check.sh`, используют локальный TLS mock,
не проверяют scheduler, CNI, CSI и admission. Проверки реального кластера —
в [инструкции](../deploy/kubernetes/README.md).

## Истечение аутентификации

`MVP_AUTH_EXPIRY_TEST=1 MVP_BROWSER_KIND=firefox MVP_BROWSER_APP=falkon
MVP_WORKER_IMAGE=mvp1-worker:pilot MVP_BROWSER_LAN_IP=YOUR_LAN_IP
./testing/browser-check.sh` (переменные и команда в одной строке) дополнительно
просрочивает auth_sessions только в созданной тестом временной БД. Проверяются
отказ API 401, закрытие медиаклиента, форма входа и повторная аутентификация.
Граница часа и отсутствие продления проверяются store-тестом с управляемым временем.
