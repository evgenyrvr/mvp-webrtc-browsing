# ADR-012: публикации сайтов и отдельная сеть приложения

Статус: принято. Выбор отдельных контейнеров/Pod подтверждён пользователем.

## Решение

Новая публикация сайта содержит название, Firefox/Falkon, стартовый HTTP(S)
URL, домены, IP/CIDR и TCP-порты. Доступ назначается существующим механизмом
ролей; для индивидуального доступа используется отдельная роль пользователя.
Название публикации показывается на карточке и в сеансе.

Для каждой такой публикации runner создаёт два контейнера или два отдельных
Pod. App содержит браузер, Xvfb, Openbox, FFmpeg и Go agent. Worker содержит
Pion, Go egress proxy с неизменяемыми правилами сеанса и Go IPP. Между ними:

- worker → app TCP 8090: аутентифицированные структурированные события ввода
  и поток IVF/VP8; не общий X11 TCP и не общая файловая система;
- app → worker TCP 8082: HTTP proxy и HTTPS CONNECT;
- app → worker TCP 8631: IPP из локального перенаправителя печати.

Agent имеет отдельный токен. Токен control API и TURN credentials не передаются
в app. Приложения запускаются UID 1000 с очищенным окружением. NET_ADMIN и
NET_RAW не требуются. Оба экземпляра имеют прежний предел жизни 30 минут.

Docker: отдельная internal bridge сеть каждого сеанса с gateway mode isolated,
без адреса host на bridge. Worker подключён также к основной сети, IP forwarding
в нём выключен. Proxy/IPP проверяют исходную подсеть, чтобы не обслуживать другие
контейнеры основной сети. Необходим Docker с поддержкой isolated gateway mode;
при отказе создания сети запуск завершается ошибкой, без ослабления режима.

Kubernetes: отдельные Pod с уникальными метками пары и NetworkPolicy, созданными
до Pod. App не разрешён внешний DNS, выход к другим Pod или напрямую к сайтам.
Worker разрешён TCP-выход для proxy; DNS и TURN регулируются общей политикой.
SQLite остаётся в единственном control Pod. Между app и worker не требуются
общие volumes, поэтому возможно размещение на разных узлах.

## Семантика правил

`dion.vc` — только это имя. `*.dion.vc` — поддомены всех уровней, без apex.
Пустая политика запрещает назначения. Для частного адреса необходимо явное
разрешение CIDR, даже если домен разрешён. Для корпоративного имени укажите
и домен, и его частную подсеть. Для URL с IP достаточно соответствующего CIDR.
Proxy проверяет DNS и подключается к уже проверенному числовому адресу.
Loopback, link-local, multicast и служебные protected_cidrs запрещены независимо
от пользовательских правил. Proxy не использует системные HTTP_PROXY.

HTTPS не расшифровывается: правила ограничивают назначения и порты, не пути URL,
содержимое или протокол внутри CONNECT. Перенаправления/CDN/SSO требуют собственных
разрешений. QUIC напрямую недоступен; браузер использует TCP через proxy.

Изменение публикации атомарно помечает её активные сеансы stopping. Runner удаляет
пару, закрывая ранее открытые туннели; пользователь запускает приложение заново.
Новые публикации не получают разрешений ролей автоматически.

## Совместимость и эксплуатационные границы

Существующие общие Falkon/Firefox/terminal сохранены без изменения их сетевого
режима. Они не приобретают ограничения новой публикации. Администратор должен
отозвать общие браузеры у ограниченных пользователей и выдать новые карточки.

NetworkPolicy требует поддерживающего её CNI. Разрешения других политик
складываются; широкие namespace-wide allow правила могут нарушить изоляцию.
Стандартная NetworkPolicy не гарантирует блокировку всех служб своего узла:
для строгой корпоративной границы нужны host firewall/CNI host policies и
проверка metadata/node endpoints. protected_cidrs необходимо заполнить сетями
Pod, Service, узлов и управления; Pod CIDR и TURN IP добавляет renderer.

Внутренний HTTP transport доверяет инфраструктуре Docker/кластера. Он не заменяет
mTLS против перехвата скомпрометированным узлом. Это отдельная будущая задача.
