# ADR-003: подготовка к отдельному API gateway

Статус: принято как направление развития; продукт и срок перехода не выбраны.
Дата: 2026-09-17.

## Контекст

В пилоте Go gateway совмещает публичный HTTP/WSS вход, UI и прикладную логику.
В будущем необходим переход к API gateway. Текущий Go gateway и будущий
инфраструктурный API gateway имеют разные обязанности.

## Решение

В пилоте сохраняется один Go gateway. Внутри него транспортные обработчики
отделяются от сервисов аутентификации, ролей, каталога и управления сеансами.
Публичный API получает пространство `/api/v1`; бизнес-логика не зависит
от конкретного прокси или поставщика API gateway.

Целевая схема управления:

```text
Chrome → API gateway → Go application backend → runner / workers
```

API gateway будет отвечать за внешний вход, TLS, маршрутизацию HTTP/WSS,
общие ограничения запросов и наблюдаемость. Go backend сохраняет проверки
владения сеансом и прав на приложение, управление runtime и сигналинг.
Проверка входа на gateway не заменяет предметную авторизацию backend.

Медиапуть и DataChannels остаются между браузером и Pion worker, напрямую
или через coturn. HTTP API gateway не включается в тракт WebRTC-медиа.
WSS остаётся отдельным долгоживущим соединением с поддержкой upgrade и таймаутов.

## Подготовка в пилоте

- Явные контракты API и сигналинга, стабильные идентификаторы сеансов.
- Конфигурируемые публичный origin, адрес сигналинга и доверенные proxy.
- Проверка proxy-заголовков только от доверенного входа; клиент не может
  назначать себе пользователя или роль через заголовки.
- Same-origin UI/API при первом переходе, чтобы не менять cookie-аутентификацию
  и CSRF-модель без необходимости.
- Прикладные сервисы не хранят состояние пользовательского приложения
  в HTTP/WebSocket-обработчике: им управляет реестр app_sessions.

## Последствия и границы

Добавление API gateway не требует немедленного выделения микросервисов,
замены SQLite или внедрения JWT. Продукт API gateway выбирается позже.
Если появятся несколько Go backend, отдельно потребуется решить владение
сеансами, маршрутизацию WSS/worker-соединений и общее состояние. Наличие
API gateway само по себе не делает текущий backend горизонтально масштабируемым.

Проверка перехода: неизменные сценарии login, каталог, запуск, reconnect,
параллельные вкладки и печать через новый внешний вход.
