# Запуск пилота

## Доступ с другого компьютера в локальной сети

Остановить старые `testing/run.sh` и `testing/runtime.sh`, затем из корня:

```bash
./testing/lan.sh SERVER_LAN_IP
```

Здесь `SERVER_LAN_IP` — placeholder: замените его на LAN-адрес своего сервера. Открыть **https://SERVER_LAN_IP:8443** на клиентском компьютере.
Используется существующая `testing/data/mvp1.db`, поэтому логин и пароль сохраняются.
Для пустой БД предварительно задать bootstrap-переменные, описанные ниже.

Скрипт создаёт временный самоподписанный сертификат на 30 дней. При первом
открытии браузер покажет предупреждение о доверии: для теста подтвердить
исключение на этот адрес либо установить сертификат как доверенный.
Для рабочего запуска нужен сертификат, которому доверяют клиенты.

Gateway слушает `0.0.0.0:8443`, worker объявляет LAN-IP сервера. Между
компьютерами должны проходить **TCP 8443** и **UDP 50300–50303**. Скрипт не
меняет firewall машины или маршрутизатора. Для доступа из другой сети через
NAT понадобится отдельно настроенный TURN; этот запуск проверяет LAN.

Сеть Docker `mvp1-testing-lan` — обычная bridge-сеть с выходом через хост,
в отличие от изолированного localhost-стенда. Namespace контейнеров и socket
отдельные; БД та же тестовая. Не запускать два gateway с этой БД одновременно.
Остановка скрипта Ctrl+C завершает gateway, runner и его приложения.

## Изолированный локальный стенд (диагностика в Chromium)

Нужны Linux, Go (либо проектная установка `.tools/go`), Docker с доступным
socket и GCC для race detector. Из корня проекта:

```bash
./testing/build-worker.sh
./testing/runtime.sh
```

Runner остаётся в первом терминале. Во втором терминале:

```bash
export MVP_ADMIN_LOGIN=admin
read -rsp 'Пароль первого администратора: ' MVP_ADMIN_PASSWORD
export MVP_ADMIN_PASSWORD
./testing/run.sh
```

Открыть http://127.0.0.1:8080. Bootstrap создаёт администратора только в пустой
БД. Войти, открыть Firefox, вернуться в каталог и открыть терминал в другой
вкладке. У администратора эти приложения разрешены изначально; обычному
пользователю назначить роль и разрешения через администрирование.

Порядок важен: gateway обнаруживает socket runner при старте. Если запустить
runner позже, перезапустить gateway. Без runner каталог и администрирование
доступны, запуск приложения возвращает 503.

В Firefox на этой машине ICE-подключение к bridge IP из этого режима не
установилось; для ручной проверки Firefox используйте LAN-запуск выше.

Тестовая сеть `mvp1-testing` создаётся с `--internal`. Firefox показывает
встроенную страницу; произвольный выход в Интернет не предусмотрен. Профили
и домашний каталог временные. Остановка приложения удаляет контейнер.

## Проверки

```bash
./testing/check.sh
python3 testing/smoke.py
./testing/rtc-check.sh
./testing/docker-check.sh
./testing/browser-check.sh
MVP_BROWSER_KIND=firefox ./testing/browser-check.sh
MVP_BROWSER_LAN_IP=SERVER_LAN_IP ./testing/browser-check.sh
```

Последний тест требует собранного `mvp1-worker:pilot`, создаёт отдельную сеть
`mvp1-integration` и контейнеры со своим namespace, затем удаляет контейнеры.
Он проверяет RTP от Firefox и терминала и ввод команды в терминал через
DataChannel. Pion-клиент не заменяет проверку декодирования видео в Chrome.

## Рабочий стенд

Использовать `deploy/runtime.sh`, затем `deploy/run.sh`. Runtime требует
`MVP_PUBLIC_IP` (IP, объявляемый клиенту для WebRTC) и `MVP_APP_NETWORK`
(существующая Docker-сеть с настроенным оператором доступом к нужным адресам).
Gateway требует `MVP_PUBLIC_ORIGIN`, `MVP_TLS_CERT`, `MVP_TLS_KEY`.
Bootstrap-переменные задаются так же, как на локальном стенде.

Для TURN в обоих терминалах задать `MVP_TURN_URL` и `MVP_TURN_SECRET`.
Пример настроек сервера: `deploy/turnserver.conf.example`. Для проверки
принудительного relay задать gateway `MVP_RELAY_ONLY=1` и проверить выбранную
ICE candidate pair на клиенте. TURN ещё требует отдельного сетевого теста.

| Назначение | Тестовый запуск | Рабочий запуск |
| --- | --- | --- |
| HTTP / HTTPS | 127.0.0.1:8080 | 0.0.0.0:8443 по умолчанию |
| Media UDP | 50000–50003 | 51000–51003 |
| Runner socket | testing/data/runner.sock | deploy/data/runner.sock |
| SQLite | testing/data/mvp1.db | deploy/data/mvp1.db |

В рабочей маршрутизируемой сети Worker HTTP публикуется на случайном
loopback-порту и защищён токеном; его не нужно открывать клиентской сети.
В локальной internal-сети Docker 29 не публикует порты: runner и локальный
WebRTC-клиент используют bridge IP контейнера напрямую. Этот режим рассчитан
на браузер на том же Linux-хосте; для удалённого клиента нужна рабочая сеть. TURN listener и relay-порты задаются
в конфигурации coturn отдельно от media UDP.

## Диагностика и остановка

`docker info` проверяет доступ к daemon; `docker ps` показывает контейнеры.
Если пользователь добавлен в группу docker, но `id` её не показывает,
нужен новый сеанс входа и перезапуск IDE. Не изменять права socket на 0666.

Остановить gateway через Ctrl+C, затем runner. Перезапуск gateway с runner
закрывает старые сеансы своего namespace: восстановление после рестарта
процессов не реализовано. Переподключение браузера имеет grace period 60 секунд.
Печать PDF пока не реализована; permission print резервирует право, но не
означает доступную функцию печати.

## Обновление уже открытых вкладок

После обновления gateway закрыть старые вкладки приложений и открыть их заново
из каталога. Старый JavaScript продолжает выполняться до перезагрузки страницы.
Если одно приложение открыто в двух местах, управление получает последнее
подключение; прежняя вкладка показывает сообщение и не переподключается сама.
При реальных кратких сетевых обрывах автоматические попытки ограничены.

Firefox получает лимит 512 задач контейнера, terminal — 256. Здесь Docker
считает процессы и потоки вместе: Firefox в проверке использовал 273 задачи,
из-за чего прежнего лимита 256 было недостаточно. CPU — 1,5 ядра, память —
1 ГБ на приложение. После изменения runtime пересобрать worker и перезапустить
LAN-скрипт, чтобы новые контейнеры получили актуальную конфигурацию.

## Виртуальный принтер

Решение: [ADR-007](adr/007-go-ipp-printing.md). Go worker принимает IPP на
`127.0.0.1:8631` только внутри контейнера; этот порт не публикуется на хосте.
Firefox получает `CUPS_SERVER=127.0.0.1:8631`. При разрешении печати готовый PDF
передаётся по каналу `print`, после чего под состоянием сеанса появляется ссылка
«Открыть PDF для печати». В открытом PDF используйте локальный диалог печати.

Лимиты: два PDF по 25 MiB на worker, срок хранения 10 минут. Закрытие сеанса
и отзыв разрешения удаляют серверную очередь. Уже открытый или сохранённый
на клиентском компьютере документ отозвать невозможно. Физический результат
печати серверу неизвестен.

## Kubernetes на Ubuntu и Falkon

Основной опубликованный браузер — Falkon; Firefox остаётся резервным. После
обновления gateway миграция SQLite добавляет Falkon с правами, скопированными
с Firefox. Пересоберите worker image: старый образ не знает шаблон `falkon`.
Профили обоих браузеров одноразовые.

Для существующего многоузлового кластера, registry, PVC, RBAC, NetworkPolicy,
TLS и coturn см. [инструкцию Kubernetes](../deploy/kubernetes/README.md).
Реальный кластер требует отдельной приёмки. Тестовую БД туда не переносить.

### CPU локального LAN-стенда

`testing/lan.sh` выделяет Falkon/Firefox до 2,5 CPU на контейнер, terminal — 1,5.
Переопределение: `MVP_BROWSER_CPUS=2.5 ./testing/lan.sh SERVER_IP`.
Это верхняя граница, не резервирование ядер. Общие Docker defaults и Kubernetes
остаются 1,5 CPU; настройки LAN не переносятся туда автоматически.

### Автоматическое завершение приложений

Все опубликованные приложения пилота закрываются через 30 минут от запуска,
включая активные сеансы администратора. Переподключение таймер не сбрасывает.
Сохраните результат до закрытия; после завершения запустите новое приложение
из каталога. Очистка и обновление статуса выполняются при очередной сверке
(обычно до 5 секунд плюс время остановки runtime). См. ADR-010.

### Хранение паролей и повторный вход

Схема SQLite 4 содержит users.password_hash (Argon2id с солью). Посмотреть исходный
пароль больше нельзя; администратор может только задать новый через интерфейс.
При первом обновлении старые пароли мигрируют, старые cookies отзываются.
Вход действует один час от аутентификации без продления при работе/refresh.
После истечения интерфейс требует логин и пароль; API и worker запрещают доступ.
Старые копии БД, сделанные до миграции, могут содержать открытые пароли.

## Публикации сайтов

В панели администратора заполните «Новая публикация сайта»: например,
идентификатор `yandex`, название «Яндекс», Firefox, URL `https://ya.ru`, домен
`ya.ru`, TCP-порт `443`. Дополнительные домены ресурсов/перенаправлений задаются
отдельно. Затем назначьте запуск/управление/печать роли. Для отдельного пользователя
выдайте ему отдельную роль с этой публикацией. IP можно указать как `192.0.2.25`
(форма преобразует его в `/32`) или CIDR. Для частного адреса домена также требуется
его CIDR. Изменение настроек закрывает активные сеансы этой публикации.

Новые карточки работают через отдельные app и worker. Старые общие карточки
Falkon/Firefox остаются без правил публикации: снимите их разрешения у пользователей,
которых требуется ограничить сайтами. Прокси ограничивает сетевые назначения,
а не URL-пути или содержимое TLS; CONNECT не гарантирует различение сайтов на
общем IP хостинга при намеренной подмене TLS SNI клиентом.

Для Docker используется internal bridge с `gateway_mode_ipv4=isolated`; локально
проверяется Docker 29.1.3. При неподдерживаемом режиме запуск не переключается
на открытую сеть. Оператор может задать `MVP_DENIED_CIDRS` (через запятую) в
окружении runner, чтобы безусловно запретить сети узлов, управления и сервисов
даже при широких разрешениях администратора публикации. В Kubernetes список
формируется renderer из `protected_cidrs`, Pod CIDR и TURN IP.

Проверка новой реализации в изолированной тестовой БД/образе:

```sh
CGO_ENABLED=0 ./tools/go.sh build -trimpath -o bin/session-worker ./cmd/session-worker
docker build -t mvp1-worker:publications-testing -f deploy/worker/Dockerfile .
MVP_PUBLICATION_DOCKER_TEST=1 ./tools/go.sh test -count=1 -run TestDockerPublication ./internal/runner
MVP_PUBLICATION_TEST=1 MVP_BROWSER_KIND=firefox MVP_BROWSER_APP=falkon MVP_BROWSER_LAN_IP=YOUR_LAN_IP MVP_WORKER_IMAGE=mvp1-worker:publications-testing ./testing/browser-check.sh
```

## Разрешение, видеопоток и курсор

Для общих приложений и публикаций сайтов в Docker/Kubernetes установлены
Xvfb 1280×720×24 и видеозахват 1280×720, 20 кадров/с. VP8/libvpx работает
в realtime: cpu-used=8, 2 потока кодирования, целевой битрейт 1800 kbit/s,
максимальный 2400 kbit/s, буфер 1200 kbit, lag-in-frames=0. Размер окна
клиента и fullscreen масштабируют видео, но не меняют разрешение на сервере.

В захвате FFmpeg отключено рисование серверной мыши (`-draw_mouse 0`):
пользователь видит один локальный курсор без ожидания кадра с сервера.
Позиции и клики по-прежнему передаются через DataChannel. Форма локального
курсора — обычная стрелка; изменения серверного курсора (текст/ссылка/ожидание)
пока не синхронизируются. Само действие на сервере сохраняет сетевую задержку.

Для применения изменения пересоберите worker image и запустите новые сеансы.
В Kubernetes обновите `worker_image` на новый уникальный тег и перегенерируйте
манифесты; для обновления CSS также пересоберите control image. Уже запущенные
сеансы продолжают использовать прежний образ.

Лимиты CPU различаются: LAN-скрипт задаёт браузерам 2,5 CPU по умолчанию,
Kubernetes app Pod — 1,5 CPU (браузер и FFmpeg в одном app Pod). Перед снижением
разрешения проверьте CPU throttling контейнера и доступные ресурсы узла.
Переход с 1280×720 на 1024×576 уменьшил бы число пикселей на 36%, но потребовал
бы согласованного изменения Xvfb, захвата и координат ввода и снизил бы чёткость
текста. Этот профиль пока не реализован; текущее разрешение не изменено.

### Chromium на одной машине с Docker

При создании или удалении контейнера Chromium под Linux может прервать
HTTP-запрос с `net::ERR_NETWORK_CHANGED` из-за изменения сетевых интерфейсов.
После резервирования сеанса сервер завершает запуск независимо от отключения
HTTP-клиента, с прежним таймаутом 30 секунд. Авторизованное завершение сеанса
также продолжается при отключении HTTP-клиента, с ограниченным временем очистки. При сетевой ошибке клиент до
35 секунд ищет единственный новый сеанс этого приложения среди своих сеансов,
исключая существовавшие перед запуском. Повторный POST автоматически не отправляется.
Если результат неоднозначен или не найден, проверьте «Активные сеансы» перед
повторным запуском. Ошибка отображается на текущей странице.

Регрессионная проверка непосредственно из Chromium (без обходного HTTP-клиента):
`MVP_BROWSER_LAN_IP=SERVER_LAN_IP MVP_BROWSER_LAUNCH_TEST=1 MVP_BROWSER_APP=firefox MVP_WORKER_IMAGE=mvp1-worker:pilot ./testing/browser-check.sh`.
Подставьте текущий LAN-адрес стенда вместо `SERVER_LAN_IP`.


### Рабочая область в одной вкладке

Запуск из каталога открывает приложение на той же странице. Верхние кнопки
переключают уже запущенные сеансы; «Приложения» возвращает в каталог для запуска
второго. Скрытое приложение продолжает работать. Кнопка «Завершить приложение»
закрывает только текущий сеанс и выбирает оставшийся, либо возвращает в каталог.
«На весь экран» увеличивает изображение выбранного приложения; Esc возвращает
управление и переключатели.

После обновления gateway обновите страницу Ctrl+Shift+R. Ранее открытые отдельные
вкладки приложений лучше закрыть, чтобы они не перехватывали управление.
Лимит остаётся прежним: два приложения, до 30 минут каждое.
